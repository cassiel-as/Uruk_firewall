# URUK Model Onboarding

This document is the human-readable guide for adding a new large-model backend
to URUK Trinity Console.

The code source of truth is `services/relay_protocol.py`. Documentation, model
skills, slash commands, and project instructions must follow that module instead
of redefining their own parseable output format.

## Core Rule

URUK uses one canonical core protocol for every autonomous self-upgrade model.

Model-specific syntax is allowed only as an adapter wrapper. The parseable output
must remain the same across Codex, Claude Desktop, API models, and future
autonomous backends.

For self-upgrade output, the canonical core is:

```text
[UPGRADE_EXECUTION_PLAN:<plan_id>]
{ ... JSON execution contract ... }

[TOOL_SPEC:<plan_id>]
name: snake_case_name
description: clear purpose and return format
category: screen|mouse|keyboard|file|state|clipboard|nav|wait|misc
args:
  - name: arg
    type: str|int|float|bool
    required: true|false
    description: purpose
python_code: |
  def execute(args: dict) -> dict:
      try:
          return {"result": "..."}
      except Exception as e:
          return {"error": str(e)}
---
```

For tool-design and review modes, use the JSON contracts generated by
`tool_design_json_contract()` and `review_json_contract()` in
`services/relay_protocol.py`.

## Adapter Policy

Adapters may change how a request is framed for a model, but not the core output
URUK parses.

Current adapters:

- `codex`: runs through `codex exec` first, with a read-only sandbox and
  ephemeral session. It wraps the request in `CODEX_RESPONSE`, `CODEX_STATUS`,
  and `CODEX_FLAGS`, and asks Codex to use the relevant `uruk-codex-*` skill.
  Desktop UI automation is a fallback only if the CLI is unavailable.
- `claude`: prefixes `/uruk-relay` and adds a model adapter block for structured
  modes.
- `claude_code`: uses a plain review/proposal prompt for upgrade mode. It does
  not receive a bracketed adapter block, does not use the Codex envelope, and is
  treated as candidate-tool generation rather than an autonomous install backend.
  Its output may omit `UPGRADE_EXECUTION_PLAN`; `upgrade_engine.py` falls back to
  the local default execution contract and still requires parseable
  `[TOOL_SPEC:<plan_id>]` blocks.
- `copilot`: uses the Windows Copilot desktop app as a human-facing context
  relay. It is useful for Windows UI, screenshots, file search, and settings
  guidance, but should stay out of autonomous self-upgrade failover unless a
  future stable API and parser validation path are added.
- other future models: add a new adapter branch only if the model needs a
  different request wrapper.

Do not add a second parser format for a new model. Fix the adapter prompt or the
model skill instead.

## Skill Policy

If a model supports skills, project instructions, slash commands, or equivalent
persistent instructions, create one that points back to the canonical protocol.

Skills are reinforcement, not the security boundary. The safety boundary is:

```text
services/relay_protocol.py
        -> model adapter prompt
        -> optional model skill
        -> parser validation
        -> deterministic install/test/log
        -> loop health check
```

A model without skill support may still be used if its adapter and sample output
tests pass.

## Onboarding Checklist

Before adding a model to autonomous self-upgrade failover:

1. Add or confirm its runtime profile in `config/nodes.yaml`.
2. Add a model adapter branch in `services/relay_protocol.py` if needed.
3. If the model supports persistent instructions, add a dedicated skill or
   equivalent instruction set.
4. Run the relay protocol tests:

   ```powershell
   py -m unittest tests.test_relay_protocol
   ```

5. Send a sample `UPGRADE_PLAN` prompt to the model and verify the response
   contains one `UPGRADE_EXECUTION_PLAN` block followed by one or more
   `TOOL_SPEC` blocks using the exact plan id.
6. Confirm `upgrade_engine.parse_claude_response()` and
   `apply_execution_plan_from_response()` can parse the sample response.
7. Confirm the self-upgrade loop health gate accepts the result before adding
   the model to a self-upgrade failover chain.

Claude Code-specific check:

- Use `plan` permission mode and read-only tools (`Read,Glob,Grep`).
- Ask for reviewable candidate `[TOOL_SPEC:<plan_id>]` blocks, not automatic
  installation.
- If Claude Code returns a subscription/session limit error, mark the plan
  failed with a human-readable summary and expose `fallback_target: codex`
  instead of leaving the plan in `waiting_claude`.
- Do not auto-drive the current Codex Desktop UI as a hidden fallback from a
  Claude Code limit failure; the user should explicitly select Codex or another
  relay in the UI.

## Failure Rules

Do not add a model to self-upgrade failover if any of these are true:

- It cannot reliably include the exact plan id in every canonical block.
- It emits only prose or markdown fences around parseable blocks.
- It omits `UPGRADE_EXECUTION_PLAN`, unless it is explicitly configured as a
  proposal-only backend like Claude Code and the local default execution
  contract is acceptable.
- It proposes code that needs shell execution, credential access, destructive
  file operations, network downloads, process killing, or core-file edits.
- It cannot produce `execute(args: dict) -> dict`.
- It passes a prompt-only check but fails parser validation or loop health
  checks.

In those cases, keep the model available for general relay or manual review, but
do not use it as an autonomous self-upgrade backend.
